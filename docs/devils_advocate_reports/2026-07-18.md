### Issue #2: `first-boot` Violates INV-7 — Checksum Failures Are Logged, Not Enforced
* **Category:** Conflicts
* **Location:** `cx-distro/distro/first-boot`, lines 91–107 and line 360
* **The Flaw:** INV-7 states "If any checksum fails, the script MUST refuse to start the inference server." The `first-boot` script finds checksum failures, calls `err()` (which only writes to syslog and stderr), and then **continues executing**. It polls the PB and QB health endpoints (Steps 2, 2b), runs the harvest, adds the user to groups, writes the boot-report JSON, queues the desktop notification, and then writes the "first-boot complete" sentinel at line 360 — unconditionally, even when `OVERALL_STATUS="red"`. Compare this to `build.sh` lines 148–151, which correctly calls `die()` on checksum failure and aborts. The `first-boot` script never stops the inference server, never calls `systemctl stop`, and never exits with a non-zero code on checksum failure. The "defense-in-depth" verification mandated by INV-7 has no teeth: it reports and moves on.
* **The Fix:** After the checksum phase (line 101), if `CHECKSUM_FAILURES -gt 0`, stop the running inference services (`systemctl stop icebreaker-pbd.service icebreaker-qbd.service`) and exit with a non-zero code **before** polling health or writing the sentinel. The sentinel must only be written when all required phases pass. Model the abort on `build.sh`'s `die()` pattern.

### Issue #3: `risk_classifier.py` TOCTOU — `realpath()` Called Twice on the Same Target
* **Category:** Code/Architecture
* **Location:** `dual-brain/controller/risk_classifier.py`, lines 142–149
* **The Flaw:** `classify()` calls `_target_is_critical(target)` at line 142. Internally, `_target_is_critical()` calls `os.path.realpath(target)` at line 105 to resolve symlinks. Then, on line 143, `classify()` calls `os.path.realpath(target)` a **second time** to compute `blocked_pattern`. Between these two calls, a local attacker with filesystem access could atomically replace a symlink (`/tmp/link → /home/user/file` becomes `/tmp/link → /etc/shadow`). The first call returns the benign path (check passes), the second call returns the critical path. The audit log's `blocked_pattern` would then record a path that was never actually blocked — corrupting the audit record and potentially misleading the human reviewer. This is a TOCTOU (time-of-check, time-of-use) race condition on the security-critical path.
* **The Fix:** Resolve the path exactly once at the start of `classify()`, store the resolved string, and pass it to both `_target_is_critical()` and the `blocked_pattern` extraction. Alternatively, have `_target_is_critical()` return a tuple `(is_critical: bool, resolved_path: str)` so the resolved value is reused.

### Issue #4: `hitl.py` `lockout()` Uses `time.sleep()` Instead of a Monotonic Clock (BP-4 Violation)
* **Category:** Code/Architecture
* **Location:** `dual-brain/controller/hitl.py`, lines 238–248
* **The Flaw:** BP-4 explicitly requires: "enforce the approval lockout on a **monotonic clock** (INV-6)." The `lockout()` method instead counts down using a `for remaining in range(seconds, 0, -1)` loop with `time.sleep(1)` per iteration. This has two failure modes. First, under QEMU/TCG emulation (used by the project's own QEMU gate), virtual clock drift means a 3-second lockout may complete in significantly less wall-clock time. Second, the loop counts iterations, not elapsed time — if any iteration's `print()` call or system load causes the iteration to take less than 1 second AND the sleep is not perfectly aligned, the lockout expires early. The `read_decision()` method correctly uses `time.monotonic()` (line 264) for its timeout, making the inconsistency worse: the lockout that precedes it doesn't share the same rigor.
* **The Fix:** Replace the sleep-counting loop in `lockout()` with monotonic clock enforcement: record a start time via `time.monotonic()`, loop until `time.monotonic() - start >= seconds`, and display remaining time by computing `seconds - (time.monotonic() - start)`. This is exactly what `_read_loop()` does — apply the same pattern to `lockout()`.

### Issue #5: `audit.py` `write()` Mutates the Caller's Dict in Violation of the `Mapping` Type Contract
* **Category:** Code/Architecture
* **Location:** `dual-brain/controller/audit.py`, lines 477–506 (specifically lines 498–499)
* **The Flaw:** The method signature declares `entry: Mapping[str, Any]`. `Mapping` is the **read-only** abstract interface; it does not guarantee `__setitem__`. Yet lines 498–499 directly write to the entry: `entry["seq"] = self._last_seq` and `entry["prev_hash"] = self._last_hash`. This has two concrete consequences. First, it is a type contract violation — code passing a `MappingProxyType` or any other immutable mapping would crash here. Second, it silently mutates the caller's dict. If a caller constructs an entry via `make_entry()`, stores the result, then calls `write()`, their stored dict is now contaminated with `seq` and `prev_hash` fields they didn't add. Reusing or inspecting that dict afterward produces unexpected results. The audit layer is a security-critical component; surprising side-effects in it are unacceptable.
* **The Fix:** Either change the type hint to `MutableMapping[str, Any]` / `dict[str, Any]` to accurately reflect the mutation, or (better) build a local copy inside `write()` before stamping it: `stamped = {**entry, "seq": self._last_seq, "prev_hash": self._last_hash}`, serialize `stamped`, and never mutate the caller's object.

### Issue #6: `workflow_gen.py` Scratch Directory Created World-Listable
* **Category:** Code/Architecture
* **Location:** `dual-brain/rpa_bridge/workflow_gen.py`, lines 162 and 270
* **The Flaw:** The default scratch directory is `/tmp/icebreaker-rpa/` (line 162), which sits inside `/tmp` — a world-writable, sticky-bit directory accessible by every user on the system (per Chapter 4, Section 4.2 of the project's own Linux guide). Line 270 creates the directory with `self._scratch.mkdir(parents=True, exist_ok=True)` — no `mode` parameter is supplied. Under a default umask of `0022`, this creates the directory with permissions `0755` (world-readable and world-listable). Any local user can `ls /tmp/icebreaker-rpa/` and enumerate what `.robot` workflow files exist, even though the files themselves are `0o600`. Worse, a malicious local user can pre-create `/tmp/icebreaker-rpa/` with `0777` permissions before icebreaker does, defeating the intended isolation (TOCTOU on directory creation). The linux_complete_guide Chapter 6.9 explicitly demonstrates `(umask 077; mkdir dir)` for sensitive directories.
* **The Fix:** Pass `mode=0o700` to `mkdir()`: `self._scratch.mkdir(parents=True, exist_ok=True, mode=0o700)`. Also move the default scratch dir from `/tmp/icebreaker-rpa/` to a location under `$XDG_RUNTIME_DIR` (e.g., `/run/user/<uid>/icebreaker-rpa/`) which is user-private by design. If `/tmp` must be used, create a per-session subdirectory with a random suffix to prevent pre-creation attacks.

### Issue #7: `intent_store.py` Has No Maximum Entry Count (BP-10 Violation)
* **Category:** Code/Architecture
* **Location:** `dual-brain/controller/intent_store.py`, lines 63–68 (`put()`) and lines 111–118 (`evict_expired()`)
* **The Flaw:** `put()` appends to `self._store` without any limit check. `evict_expired()` must be called explicitly — it is never triggered by `put()` itself. BP-10 states: "Bound untrusted input size, turn/request rate, and per-session cost. On limit breach, deny/abort + audit + surface to the user — never silently drop." A misbehaving QB backend in an error-retry loop, or an adversarial session, can call `put()` thousands of times, filling the process heap with unreaped intent objects. The TTL is 5 minutes (line 23), so entries live long enough for a fast loop to exhaust memory before expiry. The store is a singleton (`_store` at line 126) shared across the entire process lifetime. There is no size telemetry, no admission gate, and no backpressure signal to the orchestration layer.
* **The Fix:** Add a `max_entries` parameter (default e.g. `256`) to `IntentStore.__init__()`. In `put()`, after acquiring the lock, call `evict_expired()` first (lazy GC), then check `len(self._store) >= self._max_entries` and raise a bounded exception (audited as `LIMIT_EXCEEDED`) if the limit is reached. Log the limit breach to the audit trail per BP-10.

### Issue #8: `service.restart` Auto-Executes at Tier 2 — No HITL Required
* **Category:** Conflicts
* **Location:** `dual-brain/controller/_mcpd_tools.py`, lines 69–75; `dual-brain/controller/risk_classifier.py`, lines 182–188
* **The Flaw:** `service.restart`, `service.start`, and `service.stop` are in `SYSTEM_WRITE_TOOLS` (confirmed in `_mcpd_tools.py` lines 73–75). In `risk_classifier.py` lines 182–188, `SYSTEM_WRITE_TOOLS` maps to `Tier.MEDIUM` (auto-execute + notification only). `ClassificationResult.requires_hitl` returns `False` and `auto_execute` returns `True` for Tier 2. This means the AI can restart the SSH daemon, the display manager, the `icebreaker-daemon` service itself, or `icebreaker-pbd.service` — all without any human approval gate. Restarting SSH during an active remote session terminates the connection. Restarting the controller mid-session destroys all session state. This contradicts the project's "graduated determinism" philosophy and stands in direct tension with the care taken to require HITL for `fs.write` outside `$HOME`. A service restart can be more disruptive than many file writes, yet it bypasses the approval mechanism entirely.
* **The Fix:** Move `service.restart` and `service.stop` to a conditional tier (like `fs.write`) or promote them to Tier 3 by default, with a scoped exception for non-critical services (e.g., user-owned systemd units). At minimum, add a blocklist of critical service names (`sshd`, `icebreaker-daemon`, `icebreaker-pbd`, `icebreaker-qbd`, display managers) that force Tier 3 regardless of tool classification.

### Issue #9: `build.sh` Mutates `checksums.sha256` Mid-Build, Breaking INV-7 Chain of Custody
* **Category:** Conflicts
* **Location:** `cx-distro/build.sh`, lines 234–247; `cx-distro/rebuild/rebuild.sh`, line 98
* **The Flaw:** Stage 1 of `build.sh` modifies `${REPO_ROOT}/models/checksums.sha256` in-place (lines 234–246) by injecting freshly computed mcpd binary hashes. Meanwhile, `rebuild.sh` line 98 deploys the repository to the GCP build VM via `git archive HEAD`, which by definition captures only committed state (this is PKG-8 verbatim). On any subsequent `rebuild.sh` invocation, the tarball from `git archive HEAD` overwrites the VM's `checksums.sha256` with the pre-Stage-1 version (no mcpd entries). Stage 0 of the new build run verifies only GGUF model hashes (since mcpd entries aren't in git HEAD yet), then Stage 1 adds new hashes again. The critical consequence: if the build fails between Stage 1 and ISO packaging, the on-disk `checksums.sha256` on the VM has mcpd hashes but the ISO does not yet exist. There is no explicit gate verifying that the `checksums.sha256` embedded in the ISO matches what's in the git repository, which INV-7 requires as the "authoritative hash manifest."
* **The Fix:** Separate the mcpd hash computation from `checksums.sha256` modification. Write mcpd hashes to a separate build-time file (e.g., `cx-distro/.build/mcpd-checksums.sha256`). During ISO packaging (Stage 4/5), merge `models/checksums.sha256` and `cx-distro/.build/mcpd-checksums.sha256` into the chroot's copy without touching the source repo. This preserves `git archive HEAD` fidelity and keeps `models/checksums.sha256` in a stable, committable state.

### Issue #10: `gui_agent/sandbox.py` Grants `AF_NETLINK` Without Documented Justification — Potential Over-Privilege
* **Category:** Code/Architecture
* **Location:** `dual-brain/gui_agent/sandbox.py`, lines 148 and 213–224
* **The Flaw:** The module docstring lists the seccomp policy as: "Allow `socket(AF_UNIX)`" — AF_NETLINK is not mentioned. Yet line 148 adds `_AF_NETLINK` with the comment "D-Bus needs it" and lines 213–224 add an explicit ALLOW rule for `socket(AF_NETLINK, ...)`. AF_NETLINK is the kernel interface for routing tables, netfilter/iptables rules, udev device events, audit subsystem communication, and more. Granting it to a GUI agent whose only stated need is AT-SPI D-Bus communication is a significant privilege overgrant. The claim "D-Bus needs it" is neither cited nor verified in the code — the D-Bus session bus communicates over AF_UNIX sockets, not netlink. BP-9 states: "Grant the narrowest filesystem/syscall/network scope that works; widen only with documented justification." The AF_NETLINK rule was added without that justification. The `rpa_bridge/sandbox.py` docstring mentions AF_UNIX only, reinforcing that netlink is exceptional and unexplained here.
* **The Fix:** Remove the AF_NETLINK allowance and test whether AT-SPI / D-Bus functionality breaks. If it does break, identify the exact call path that requires it (which library, which syscall, which condition) and document it with a comment referencing the specific issue. If it doesn't break, the rule was never needed. If AF_NETLINK is genuinely required by some D-Bus implementation quirk, scope the seccomp rule to the minimum required netlink family (`NETLINK_KOBJECT_UEVENT` for udev only, rather than unrestricted AF_NETLINK) and add a regression test that verifies the GUI agent still works when the rule is absent on systems where it isn't needed.
