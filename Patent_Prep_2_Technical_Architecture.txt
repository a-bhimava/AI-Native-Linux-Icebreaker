1. System Architecture Overview
The system is an AI-native Linux derivative in which one or more locally-hosted LLMs translate natural-language user intent into auditable, sandboxed system operations. The architecture comprises four tiers with a strict, one-directional trust gradient from untrusted input toward privileged execution.
  Untrusted input (user text, file contents, tool output)
        |
        v
  [ QUARANTINED BRAIN ]  perception model — NO tool access
        |  structured Intent Object (candidate)
        v
  [ CONTROLLER ]  (non-AI) schema-validate -> risk-classify -> HITL gate
        |          -> store intent, emit OPAQUE UUID + allowed tool + schema
        v
  [ PRIVILEGED BRAIN ]  execution model — NO raw text, only UUID-referenced intent
        |  concrete MCP tool call (validated again)
        v
  [ mcpd ]  Rust daemon — stdio JSON-RPC only, per-call schema validation
        |  fork child; apply Landlock + seccomp-BPF BEFORE execve; COW dry-run
        v
  [ LINUX KERNEL ]  mandatory access control = final enforcement
 
  Append-only audit log records every intent (incl. rejected), out-of-band of the models.
The defining property is that no single component simultaneously possesses (a) exposure to untrusted text and (b) the capability to execute. The Quarantined Brain has (a) without (b); the Privileged Brain has (b) without (a). The Controller, which has neither AI nondeterminism nor untrusted-text-to-execution authority, mediates the crossing through a validated, opaque channel.

2. Threat Model and Design Goal
Primary adversary: an attacker who controls some untrusted content the system will read (a document, web page, file name, or prior tool output) and attempts an indirect prompt-injection (confused-deputy) attack to induce privileged actions — data exfiltration, destructive writes, credential theft, or sandbox escape.
Design goal: even granting the adversary the power to fully control the Quarantined Brain's behavior (worst case: the perception model is completely subverted by the injected content), the adversary must not gain the ability to (i) cause arbitrary tool execution, (ii) exfiltrate raw data through the model channel, or (iii) escape the kernel sandbox. The defense is therefore an information-flow and capability architecture, with the kernel as the non-AI enforcement floor.

4. Quarantined Brain (Perception Tier)
A local LLM (reference embodiment: a small instruction model such as Phi-4-mini) that ingests untrusted material and emits a candidate Intent Object. It is constructed through a backend wrapper (backends/base.py) that makes execution capability structurally unreachable:
	•	Guard sentinel in the constructor. A private sentinel object gates construction; any attempt to inject an mcpd client / tool handle into a brain backend raises at construction time. This realizes INV-1 "zero tool connections" as a constructor-level invariant, not a convention.
	•	tools_disabled is non-overridable. The request envelope sets a tools-disabled flag that subclasses cannot flip; the base class forbids subclasses from overriding the completion method (via __init_subclass__) and requires __slots__ to prevent ad-hoc attribute injection.
	•	Grammar-constrained output. Output is constrained at sampling time to schema-valid Intent Objects by a GBNF grammar (controller/grammars/qb_intent.gbnf), so the perception model cannot emit free-form text that bypasses the schema.
	•	Strict JSON extraction. The backend extracts exactly one JSON object via a single brace-slice (no lenient multi-object parsing), reducing parser-confusion attack surface.
Inventive hook
The perception model's inability to act is not merely "we didn't give it tools" — it is enforced by a constructor sentinel, a non-overridable flag, a subclass-override prohibition, and __slots__. This mechanical non-bypassability is a candidate inventive concept (see §11 and CI-2 in §14).
5. Privileged Brain (Execution-Decision Tier)
A local LLM (reference embodiment: a small coder model such as Qwen2.5-Coder-1.5B, optionally fine-tuned via the Phase-4 pipeline) that receives only a minimal, opaque execution context and emits a concrete MCP tool call. Per session.py, the user-turn assembled for the Privileged Brain contains strictly: the opaque intent_id, the single allowed_tool, and that tool's tool_schema. It never receives raw user text or document content.
	•	Outbound payload auditor (fail-closed). Before any request leaves a brain backend, an OutboundPayloadAuditor (backends/auditor.py) recursively scans the payload and raises BrainSecurityError if it contains forbidden keys (tools, functions, grounding, etc.). The base backend probes the auditor's call count and raises if the auditor was skipped — so omitting the audit is itself a failure.
	•	Secret sanitization. sanitize.py strips secrets from exceptions/logs (KeyRedactionFilter on the root logger; SecretRef carries only an env-var name; SECRET_PATTERNS match sk-ant-, AIza, ya29., JWT/Bearer forms), preventing key leakage through error channels.
	•	Tool-result summaries flow only to the Quarantined Brain. Per session.py add_tool_result_summary(), mcpd output is fed back to perception for the next turn, never to the Privileged Brain — extending INV-1/INV-2 across multi-turn loops.
6. Controller (Non-AI Mediation Tier)
The Controller is deterministic software implementing the crossing between brains. Its run_turn() pipeline (controller/main.py) is a fixed ~14-step sequence; §12 lists it. Its sub-modules:
6.1 Intent schema validation (INV-2, INV-4)
intent_schema.py validates the candidate Intent Object with a Draft-7 validator plus a UUID format checker. schemas/intent.json enforces: required fields, additionalProperties:false, an action pattern of dotted lowercase tokens (^[a-z][a-z0-9_]*(\.[a-z][a-z0-9_]*)+$), and target/params patterns that forbid shell metacharacters (; & | ` $ < >) and control bytes (\x00–\x1f). reason and risk_level are enum-constrained. A non-conforming intent is rejected before it can be stored or referenced.
6.2 Opaque intent store (INV-1, INV-2)
intent_store.py is a thread-safe store mapping a freshly-generated UUID to a validated intent. put() returns the UUID; the Privileged Brain only ever receives this reference. Key properties:
	•	TTL bound (TTL_SECONDS = 300): references expire, limiting replay and stale-intent windows.
	•	revise() under a single lock: a get→merge→validate→store revision runs atomically under one lock, closing a documented race (P2-F13) where concurrent revision could admit an unvalidated intent.
	•	No new top-level keys on revision: a revision cannot introduce keys outside the schema, preventing privilege-escalation by field injection (INV-2).
6.3 Risk classifier — graduated determinism (INV-6)
risk_classifier.py maps each intent to a tier via an IntEnum (0–3). It resolves symlinks with os.path.realpath before matching (defeating symlink-TOCTOU at classification time) and matches a _CRITICAL_PATHS regex (e.g., /boot, /etc/sudoers, /etc/shadow, /root). Tool sets are derived from an auto-generated catalogue (_mcpd_tools) so classifier and daemon stay in sync.

6.4 Human-in-the-loop gate (INV-6)
hitl.py presents a COW dry-run summary (ANSI-stripped) and enforces LOCKOUT_SECONDS = 3 (Approve disabled for the first 3 seconds) and TIMEOUT_SECONDS = 30 (auto-deny on no response). The Decision enum records approve/deny/timeout. The forced lockout is an anti-"click-through" measure ensuring the human actually reads a destructive dry-run.
6.5 Non-bypassable backend base class (INV-1)
backends/base.py (BrainBackend ABC) centralizes the isolation guarantees described in §4–§5: the _GUARD_SENTINEL construction gate, __init_subclass__ forbidding complete() override and requiring __slots__, the non-overridable tools_disabled envelope flag, strict single-object JSON extraction, the auditor call-count probe, and a bounded sampling-decay retry. This class is the single chokepoint that makes brain isolation a property of the type system rather than of discipline.
7. mcpd — Hardened Tool-Execution Daemon (Rust)
mcpd executes the privileged operations. It is a Rust daemon exposing a catalogue of ~22 tools over MCP (JSON-RPC 2.0) on stdio only.
7.1 Transport isolation (INV-3)
server.rs implements a JSON-RPC 2.0 stdio dispatcher. is_known_method() gates the request; methods outside the catalogue are rejected. mcpd opens no network or UNIX-socket listener; CI asserts ss -tlnp shows no mcpd process with open ports. seccomp (below) additionally denies listen/accept at the syscall level, so even a code regression cannot open a listener — a defense-in-depth realization of INV-3.
7.2 Compile-time schema validation (INV-4)
schema.rs embeds each tool's JSON Schema at compile time (include_str!), compiles it, and validate() rejects non-conforming parameters with JSON-RPC error -32602 before dispatch. SCHEMA_VERSION is pinned (1.0.0). Because schemas are compiled into the binary, a deployed daemon cannot drift from its declared contract.
7.3 Two-layer filesystem defense (INV-4, INV-6) — the most security-critical module
tools/fs.rs implements defense in two independent layers:
	•	Layer 1 — pure validation. validate()/validate_against() reject NUL bytes, '%', backslashes, non-absolute paths, and any path outside a whitelist of roots (/proc, /sys, /tmp, /var/log, /etc, $HOME). A set of SENSITIVE_HOME_SUBDIRS (.ssh, .aws, .gnupg, …) forces the COW path even within home.
	•	Layer 2 — kernel-enforced resolution. The actual open uses openat2 with OpenHow{flags,mode,resolve} and RESOLVE_STRICT = RESOLVE_BENEATH | RESOLVE_NO_SYMLINKS, so the kernel rejects any path that escapes the intended root or traverses a symlink. This closes the TOCTOU gap between userspace validate() and use: even if validation is somehow satisfied for a path that later changes, the kernel refuses the escape.
is_tier_1_safe() classifies safe in-home writes; cow_gate_response() returns {"status":"requires_cow_approval","intent_id":<uuid>} to route destructive operations through the Controller's HITL gate. The two-layer (userspace denylist + kernel openat2) combination is a candidate inventive detail.
7.4 Landlock confinement (INV-5)
sandbox/landlock.rs builds a Landlock ABI::V1 ruleset: read-only access to the catalogue roots, read-write only to /tmp and /var/log/mcpd. If the ruleset reports NotEnforced (kernel < 5.13 or Landlock disabled), the daemon hard-exits rather than continuing unconfined — the fail-closed property of INV-5. The ruleset is applied to the execution child before execve.
7.5 seccomp-BPF dual filter (INV-5)
sandbox/seccomp.rs installs a dual filter combined with PR_SET_NO_NEW_PRIVS: a denylist (mount, reboot, ptrace, bpf, setuid, listen, accept, …) and a positive allowlist (allowed_syscalls()), with the default action being process kill. bind() is permitted (needed for netlink) while listen()/accept() are denied — reinforcing INV-3 at the kernel boundary. A harvest mode (env MCPD_SECCOMP_LOG_ONLY) supports building the allowlist during development without weakening the production default.
7.6 Copy-on-write dry-run (INV-6)
sandbox/cow.rs provides an overlay/COW dry-run for destructive operations outside home: the operation is staged so the user sees an exact diff/report before an atomic commit. Commit atomicity is required (a non-atomic commit risks corruption). The COW report is what the HITL gate (§6.4) displays under the 3-second lockout.
7.7 Audit log (INV-8)
audit.rs writes append-only JSONL (O_APPEND, mode 0640). Each AuditLine carries timestamp, intent ID, risk level, user, and a ResultClass outcome. redact() collapses non-$HOME paths to a path family and redacts content bytes; records are truncated to <= 4KB to remain within PIPE_BUF for atomic appends. The log is not writable by the model inference processes (INV-8), so a compromised model cannot erase its tracks.
7.8 Model-weight integrity gate (INV-7)
At startup mcpd verifies the SHA-256 of each GGUF model file against models/checksums.sha256 and refuses to start on any mismatch; the ISO build step verifies the same manifest before packaging. This binds the running system to known-good weights — a supply-chain integrity control integrated into the boot/execution path.
7.9 Test-only knobs are excluded from production
Hardening tests use cargo features that default off (e.g., fs-test-roots, which appends extra paths to fs default_roots only to prove the kernel — not userspace — rejects an out-of-root read). CI asserts the feature's env var string is absent from any shipped binary, and the design rule forbids gating a security check behind a feature (features may only add test surfaces, never remove production checks). This is relevant to enablement: the production security path is not weakened by test scaffolding.
8. The Opaque-Reference Inter-Brain Channel (Detailed)
This is the information-flow core. Data flow across the perception→execution boundary is reduced as follows:
Quarantined Brain  -- candidate Intent Object (JSON) -->  Controller
Controller:
   1. schema_validate(intent)          # reject metacharacters / extra fields
   2. risk = classify(intent)          # tier 0..3 (realpath-resolved)
   3. if tier == 3: HITL approve/deny  # 3s lockout, 30s timeout
   4. uuid = intent_store.put(intent)  # TTL=300s, thread-safe
   5. emit -> Privileged Brain: { intent_id: uuid,
                                  allowed_tool: <one tool>,
                                  tool_schema: <that tool's schema> }
Privileged Brain  -- concrete tool call -->  Controller -> mcpd
   (mcpd re-validates params, sandboxes, executes)
Tool result summary -> Quarantined Brain ONLY (never Privileged Brain)
The Privileged Brain's entire view of the world is the triple {intent_id, allowed_tool, tool_schema}. Raw user text and document content never appear in its context window. The channel is therefore (a) opaque (a UUID, not content), (b) schema-bounded (only validated intents are storable), (c) capability-narrowed (exactly one allowed tool per crossing), and (d) time-bounded (TTL). The combination of all four constraints on a single inter-model channel is a candidate inventive concept.

12. End-to-End Request Lifecycle
Controller.run_turn() (controller/main.py) sequences a turn approximately as follows:
	•	Receive user text + any untrusted context.
	•	Quarantined Brain produces a candidate Intent Object (grammar-constrained).
	•	Schema-validate the Intent Object (reject metacharacters/extra fields).
	•	Risk-classify (realpath-resolved) into tier 0–3.
	•	If tier 3 (or critical path / out-of-home destructive): HITL gate with 3s lockout, 30s timeout.
	•	Store the validated intent; obtain an opaque UUID.
	•	Assemble the Privileged Brain turn = {intent_id, allowed_tool, tool_schema} only.
	•	Privileged Brain emits a concrete MCP tool call.
	•	Outbound auditor scans the payload (fail-closed).
	•	mcpd re-validates parameters against the compiled schema (INV-4).
	•	mcpd forks child; applies Landlock + seccomp before execve; COW dry-run if destructive-outside-home.
	•	Execute under kernel confinement; capture result.
	•	Optional verification-brain round-trip ({verified, reason}).
	•	Append audit record (including any rejection) to the O_APPEND log; summarize result back to the Quarantined Brain only.

16. Enablement, Best Mode, and Known Limitations
	•	Implemented and exercised: the mcpd daemon and its security layers (transport, schema, two-layer FS, Landlock, seccomp, COW, audit, integrity) and the Controller modules described above. These support a robust enablement story for the security architecture.
	•	Partial / in-progress: the fine-tuned Privileged Brain (Phase 4) currently underperforms (FEH ~3.1% vs ~100% baseline). Best-mode disclosure for the execution-model embodiment should describe the architecture and the fine-tuning method without overclaiming the current fine-tune's accuracy. A general off-the-shelf coder model is a viable execution-model embodiment independent of the fine-tune.
	•	Not yet built: UX surface, ISO distribution, and final hardening (Phases 5–7). Claims should not depend on un-built embodiments for enablement.
	•	Internal-consistency cleanup: resolve the Phase-1 status discrepancy (§13) across docs before any disclosure is filed.
Bottom line for counsel
The architecture is real and substantially implemented; the security claims rest on working code. The patentability question is non-obviousness of the specific combination over Willison (2023) + CaMeL (2025) + standard Linux hardening. The strongest filings will (1) claim the N-brain isolated-role + opaque-channel + kernel-confinement combination, not the abstract dual-LLM idea; (2) lean on the concrete kernel mechanisms for §101; (3) include the dependent non-bypass, graduated-determinism, TOCTOU-safe-FS, and integrity-gate concepts as fallback positions; and (4) front-load the inventorship (AI-authored code; human conception) and CMU ownership questions. Treat the case as promising-but-uncertain, and let the firm's prior-art search make the call before committing to full international prosecution.
